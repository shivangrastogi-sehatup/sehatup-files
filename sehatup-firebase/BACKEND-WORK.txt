2. PROBLEMS FOUND (all verified against production)
--------------------------------------------------------------------------------

[P1 - SERIOUS] partial_submissions is publicly readable
  Deployed rule:  match /partial_submissions/{doc} { allow create, read, update, delete: if true; }
  "read" includes LIST. Anyone on the internet with the public web API key can pull
  all 1,177 docs: name, date of birth, phone, health metrics, recommended products.
  They can also delete them.

[P2 - SERIOUS] Deployed rules are NOT the same as the repo file
  sehatup-firebase/firestore.rules differs from what is live (last deployed
  2026-08-18 06:47 UTC). The live version has this block, the repo file does not:

      match /popup_leads/{doc} {
        allow create: if true;
        allow read, update, delete: if false;
      }

  Consequence: running `firebase deploy --only firestore` from the repo as it is
  silently breaks lead capture on the storefront popup. No error anywhere.

[P3 - SERIOUS] Any signed-in user can read and write EVERY collection
  Catch-all rule:  match /{document=**} { allow read, write: if request.auth != null; }
  That covers prescriptions, users (including roles), conversations, everything.
  Auth providers enabled: email = ON, phone = ON, anonymous = OFF.
  Phone sign-in being ON means anyone with a phone number can become "signed in"
  using the public web config, and then passes this rule.
  The quiz OTP flow uses our own functions (generateOTP / verifyOTP), so the Firebase
  phone provider may not be used by anything. Needs confirming.

[P4] TTL (auto-delete) is only half switched on
  ai_runs               expireAt field present, TTL policy ACTIVE
  nimbus_events_seen    expireAt field present, NO TTL policy  -> grows forever
  shopify_sync_claims   expireAt field present, NO TTL policy  -> grows forever
  qr_context_cache      NO expireAt field, NO TTL policy       -> grows forever

[P5] questionnaire_submissions allows public update
  Deployed rule:  allow create, update: if true;
  Needed for the post-OTP phone sync, but it means anyone who knows or guesses a
  document ID can overwrite a completed health report. Cannot list, so IDs are hard
  to guess, but it is still tamperable.

[P6] Rules for collections that do not exist
  qr_conversations (public read!) and shipments_test. Neither collection exists.
  The qr_conversations rule opens public read if anything ever gets written there.

[P7] Prescriptions live in two places
  Top-level "prescriptions" (633 docs) AND "{submissionCollection}/{id}/prescriptions"
  subcollections (the CRM writes both paths). Not yet checked which one is the source
  of truth, or whether they drift.

[P8] RED TALK is outside data sitting in prod
  29 quiz docs for an event (createdAt, score, phone, name, answers, percent). Nothing
  in this repo writes it. Collection name has a space in it.

[P9] admin_audit_logs is barely wired
  Only 1 entry exists. CRM deletes/edits are mostly not being logged.

RESTRUCTURE (decided 2026-09-14) - move off the flat root, grouped by who writes
  Full target map, migration steps and order: the "sehatUP Firestore Blueprint" page.

  Target groups:
    intake/v1/     public writes, no login   partial_submissions, submissions
                                             (+whatsapp_requests), leads, events/red_talk
    clinic/v1/     doctor role               patients, prescriptions, doctors
    admin/v1/      admin role                users/{uid}/permissions, audit_logs
    config/        admin writes              chatbot, prescription, logistics, counters
    messaging/v1/  servers write             whatsapp/{phone}/messages, web_chats/{id}/turns
    logistics/v1/  servers write             shipments/{phone}/awbs, nimbus_events
    NOT MOVED (stay at root, excluded from catch-all, TTL)
                                             ai_runs, qr_context_cache, nimbus_events_seen,
                                             shopify_sync_claims, active_whatsapp_requests
    A separate "ops" database is DEFERRED (decided 2026-09-14). Revisit only if these
    need their own backups/billing.

  Per collection, always these 5 steps:
    1 new rules live  2 dual write  3 backfill by id  4 switch readers  5 retire old path
    (keep old read-only 14 days before delete)

  Order, safest first:
    config -> admin -> logistics -> messaging -> clinic -> intake

  Things that bite during a move:
  - collectionGroup('messages') / ('awbs') match by last segment, so they return
    every doc twice between steps 2 and 5. Switch those readers at step 4.
  - Document-triggered functions (report PDF, prescription PDF) are bound to a path
    and must be redeployed for intake and clinic.
  - Collection names are hardcoded across ~7 separately deployed codebases:
    sehatup-analytics (CRM + Vercel API), sehatup-firebase functions, 8 copies of the
    questionnaire engine, n8n, whatsapp-tools, website-chatbot, shopify-elements.
    Every group move is a coordinated release of the apps that touch it.
  - The security fixes in "DO FIRST" above ship before any of this.
